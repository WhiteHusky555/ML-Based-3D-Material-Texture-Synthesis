## О проекте

Облачный сервис, который по описанию и параметрам формы создаёт **бесшовный набор PBR-карт** (albedo, normal, height, roughness, AO), готовый для Blender, Unity и Unreal Engine.

Идея — разделить ответственность: **процедурный шум задаёт форму** материала, **диффузионная модель — фактуру**, а собственный код доводит результат до бесшовных карт.

```mermaid
flowchart LR
    A["Форма<br/>процедурный шум<br/>(Перлин, Вороной)"] --> B["Генерация текстуры<br/>SD 1.5 + ControlNet + LoRA<br/>циклический padding"]
    P["Описание<br/>+ подсказки LLM"] --> B
    B --> C["Повышение разрешения<br/>Real-ESRGAN<br/>1K – 4K"]
    C --> D["PBR-карты<br/>height · normal ·<br/>roughness · AO"]
    D --> E["Экспорт<br/>Blender · Unity ·<br/>Unreal Engine"]
```

Бесшовность сохраняется на каждом этапе: периодический шум → циклический padding в UNet, ControlNet и VAE → wrap-паддинг при апскейле → wrap-фильтры при расчёте PBR-карт.

## Связь НИР и ВКР

В научно-исследовательскую работу (НИР) входят подготовка данных и обучение одной LoRA для SD 1.5 в Kaggle, разработка сервиса процедурных шумов и сборка конвейера от карты шума до комплекта PBR-карт. Конвейер включает генерацию через ControlNet, апскейл и расчёт карт. В НИР проверяются управляемость генерации, качество текстур и бесшовность.

Планируемые результаты НИР: веса LoRA, конфигурация модели, код сервиса шумов и конвейера, примеры материалов и протокол экспериментов. В тексте ВКР описывается весь этап НИР: подготовка данных, обучение LoRA, разработка сервисов и результаты экспериментов. В программной части ВКР компоненты НИР интегрируются в облачную систему. На этом этапе проверяются сквозная работа, производительность и масштабирование. [План НИР](05_Нейросетевые_модели/09_База_датасет_и_дистилляция.md).

## Архитектура

Для пользователей предусмотрен генератор на React + Three.js с Python-сервисом `web-bff`. Персонал работает на отдельном хосте в Vaadin-приложении `staff-ui` (Kotlin, Spring Boot 4), которое отображает панели и выполняет роль BFF. nginx завершает TLS, отдаёт React и маршрутизирует запросы по хосту и пути.

```mermaid
flowchart TB
    U["Пользователь<br/>React + Three.js"] -->|"app. · HTTPS / WebSocket"| G["nginx<br/>TLS · статика · маршрутизация"]
    S["Персонал<br/>браузер"] -->|"staff. · HTTPS / WebSocket"| G
    G -->|"app. /bff/"| WB["web-bff<br/>Python / FastAPI"]
    G -->|"staff. /"| SU["staff-ui<br/>Vaadin / Kotlin / Spring Boot"]
    WB --> R[("Redis<br/>сеансы и кэш превью")]
    SU --- SS["Сеанс Vaadin<br/>в памяти пода"]

    WB -->|"HTTP · чтение"| API["API-сервис<br/>материалы и оркестрация"]
    WB & SU -->|"HTTP · verify без кэша"| US["Пользователи и тарифы"]
    SU -->|"HTTP · чтение"| AD["admin-service<br/>Ktor · пресеты · версии · аудит"]
    WB -->|"HTTP"| PRE["Превью шума и подсказки"]
    WB & SU -->|"команды"| Q[("RabbitMQ")]
    Q -->|"команды владельцам данных"| API & US & AD
    Q -->|"итоги команд персонала"| SU
    Q -->|"прогресс задач"| API
    API -->|"WebSocket прогресса"| WB
    API -->|"события и постановка задач через outbox"| Q
    US & AD -->|"события через outbox"| Q
    Q -->|"noise"| NW["Шум · CPU"]
    Q -->|"gpu"| GW["Генерация и апскейл · GPU"]
    Q -->|"cpu"| PW["PBR · CPU"]
    NW & GW & PW -->|"события этапов"| Q
    NW & GW & PW --> FS[("S3<br/>карты и архивы")]
    API & US & AD --> DB[("PostgreSQL<br/>core · users · admin")]
```

Браузер получает cookie сеанса. Токены остаются на сервере, а оба BFF при защищённых запросах проверяют права через `verify` без кэша. Для `staff-ui` nginx закрепляет сеанс за подом. Чтение, аутентификация, регистрация и подписка идут по HTTP. Остальные команды изменения данных и доменные события проходят через RabbitMQ. Для сервисов с БД предусмотрены Transactional Outbox и Inbox. Прогресс пользовательских задач приходит из API-сервиса через WebSocket `web-bff`, а итоги команд персонала отображаются через Vaadin Push.

Развёртывание запланировано в Kubernetes с Helm, предварительно в Amazon EKS. Для локальной разработки предусмотрен Docker Compose. Маршруты, потоки данных и исключения описаны отдельно. [Подробная схема архитектуры](02_Архитектура_системы/README.md).

| Тариф | Бесплатный | Премиум |
|---|---|---|
| Разрешение | 1024² | 2048², 4096² |
| Шаги / варианты | 20 / 1 | 30–40 / до 4 |
| Референс-картинка, подсказки к промпту | — | ✓ |
| Хранение материалов | 7 дней | 90 дней |

Модель генерации **одна для всех тарифов**; LoRA для SD 1.5 дообучается в НИР. Персонал: **администратор** (обслуживание), **аналитик** (обезличенные показатели), **владелец** (тарифы, роли, финансы); все изменения персонала пишутся в журнал аудита.

Подробно — [02_Архитектура_системы](02_Архитектура_системы), журнал решений — [11_Решения_и_вопросы.md](02_Архитектура_системы/11_Решения_и_вопросы.md).

## Как проверить диаграммы

Проекты StarUML открываются в StarUML 6 (`.mdj`) или StarUML 5.0 (`.uml`). Автоматическая проверка раскладки любой диаграммы из `.mdj` (Python 3.11+):

```bash
cd 04_Лабораторные_UML/_инструменты && python -I mdj_render.py --check ../ЛР6_Диаграмма_коммуникации/01_Модель/ЛР6_Коммуникации.mdj
```
