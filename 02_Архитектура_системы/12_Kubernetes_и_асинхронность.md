# Асинхронность и горизонтальное масштабирование в Kubernetes

Требование автора (14.10.2026): **все сервисы работают асинхронно и масштабируются в ширину; вся система запускается в Kubernetes.**

## 1. Что значит «асинхронно» в этой системе
1. **Неблокирующий ввод-вывод** во всех Python-сервисах: FastAPI с `async def`, `asyncpg` / async SQLAlchemy, `aio-pika` для RabbitMQ, `httpx.AsyncClient` для HTTP, `aioboto3` для S3.
2. **Долгие операции — только через очереди.** `POST /api/materials` не ждёт генерации: ставит задачу и сразу отвечает `202 Accepted` с id задачи. Прогресс приходит по WebSocket.
3. **Тяжёлые вычисления не блокируют event loop.** Где расчёт идёт внутри HTTP-сервиса (превью шума), он выносится в пул процессов (`run_in_executor` с `ProcessPoolExecutor`).
4. **Побочные действия — фоновыми задачами:** письма подтверждения, удаление просроченных файлов, обработка webhook оплаты.

## 2. Как работает каждый сервис
| Сервис | Взаимодействие | Как устроена асинхронность | Как масштабируется |
|---|---|---|---|
| nginx (шлюз) | HTTP, WebSocket | событийная модель nginx | Deployment ×2+, HPA по CPU |
| Веб-клиент | — | статика + WebSocket | раздаёт nginx / CDN |
| API-сервис | HTTP, WebSocket, RabbitMQ | async FastAPI, aio-pika; ответ `202` + id задачи | HPA по CPU / числу запросов |
| Сервис пользователей | HTTP | async FastAPI, asyncpg; письма — через очередь | HPA по CPU |
| Процедурный сервис, API превью | HTTP | async FastAPI + пул процессов для Numba | HPA по CPU |
| Процедурный сервис, воркер | очередь `noise` | Celery-воркер | **KEDA** по длине очереди |
| GPU-воркер (генерация + апскейл) | очередь `gpu` | Celery, одна задача на видеокарту | **KEDA** по длине очереди + Karpenter добавляет GPU-узлы |
| PBR-сервис | очередь `cpu` | Celery-воркер | **KEDA** по длине очереди |
| Ассистент промптов | HTTP → LLM | async FastAPI + httpx; семафор на число одновременных вызовов LLM | HPA по CPU |
| Очистка по сроку хранения | — | **Kubernetes CronJob** (не Celery beat: при нескольких репликах beat дублировал бы задачи) | 1 запуск по расписанию |

## 3. Новый конвейер (полностью через очереди)
```
POST /api/materials ──► API-сервис: проверка тарифа и кэша ──► 202 {job_id}
                                │
                                ▼  Celery chain (приоритет по тарифу)
        noise (очередь noise) → generate → upscale (очередь gpu) → pbr (очередь cpu)
                                │
                     события job.<id>.<stage> → exchange job.events
                                │
              ┌─────────────────┴──────────────────┐
   общая очередь status-updates           личная очередь каждой реплики API,
   (конкурирующие потребители:            привязанная к job.<id>.# только для задач,
    событие пишется в БД один раз)        чьи клиенты подключены к этой реплике → WebSocket
```
- Шум для конвейера теперь тоже идёт **через очередь** (раньше API-сервис запрашивал его синхронно).
- **Масштабирование WebSocket без «липких» сессий:** каждая реплика API-сервиса при подключении клиента привязывает свою временную очередь к `job.<id>.#`. Событие дойдёт до той реплики, где открыт сокет, а запись в БД делает ровно один потребитель общей очереди.

## 4. Требования к сервисам, чтобы масштабироваться в ширину
- **Без локального состояния:** файлы — в S3, сессии — в JWT, данные — в PostgreSQL.
- **Идемпотентность задач:** ключи объектов в S3 детерминированы id задачи; повторная доставка (`acks_late`) просто перезапишет тот же объект.
- **Квоты** считаются атомарным `UPDATE … RETURNING` в PostgreSQL, а не в памяти реплики.
- **Лимиты nginx** (`limit_req`) работают на каждую реплику отдельно — это грубая защита; точные квоты — в API-сервисе.
- **Кэши в памяти** (ответы ассистента) — только как ускорение; источник правды — БД. При необходимости общий кэш — Redis (Amazon ElastiCache).
- **Пробы:** readiness — только после прогрева Numba и загрузки моделей; liveness — простая проверка процесса.
- **Корректная остановка GPU-воркера:** на SIGTERM дописать текущую задачу (`terminationGracePeriodSeconds` больше максимального времени задачи). Если узел отобрали (spot) — задача без подтверждения вернётся в очередь.

## 5. Состав кластера
| Компонент | Назначение |
|---|---|
| **Helm-чарт `texgen`** | вся система одной командой: `helm install texgen ./chart -f values-aws.yaml` |
| `values-local.yaml` | локальный кластер (k3d / minikube / Docker Desktop), без GPU — заглушка GPU-воркера или маленькая модель |
| `values-aws.yaml` | облако AWS (EKS) |
| Шлюз | **свой nginx** как Deployment + Service типа LoadBalancer (AWS NLB через AWS Load Balancer Controller). Конфиг тот же, что в Docker Compose, включая `auth_request` |
| Альтернатива шлюзу | Kubernetes **Gateway API** (NGINX Gateway Fabric, Envoy Gateway, Traefik). **Не использовать ingress-nginx**: проект официально выведен из поддержки в марте 2026 г. |
| NVIDIA device plugin / GPU Operator | выдача видеокарт подам (`nvidia.com/gpu: 1`) |
| **KEDA** | масштабирование воркеров по длине очередей RabbitMQ (в т. ч. до нуля) |
| **Karpenter** (или Cluster Autoscaler) | добавление и удаление узлов, в т. ч. GPU-узлов и spot |
| cert-manager | TLS-сертификаты (или сертификат ACM на балансировщике) |
| External Secrets Operator | секреты из AWS Secrets Manager |
| kube-prometheus-stack + DCGM exporter | метрики кластера и видеокарт, Grafana |
| Flower | мониторинг Celery |
| Внешние управляемые сервисы | PostgreSQL — Amazon RDS; S3 — Amazon S3; RabbitMQ — Amazon MQ или RabbitMQ Cluster Operator внутри кластера |

## 6. Локальная разработка
- **Docker Compose остаётся** для быстрой разработки одного разработчика (MinIO вместо S3, RabbitMQ и PostgreSQL в контейнерах).
- Проверка Kubernetes-манифестов — локальный кластер k3d / minikube с `values-local.yaml`.
- Код не меняется между окружениями: адреса S3, БД, брокера и провайдера LLM задаются переменными окружения.

## 7. Что измерить в ВКР (дополнение к экспериментам)
- Пропускная способность (материалов в час) при 1, 2, 4 GPU-воркерах — подтверждает горизонтальное масштабирование.
- Время ожидания в очереди для премиум и бесплатных задач при нагрузке — подтверждает приоритеты.
- Время подъёма нового GPU-воркера (узел + загрузка моделей) — «холодный старт».
- Задержка превью шума при 1 и N репликах процедурного сервиса под нагрузкой.
