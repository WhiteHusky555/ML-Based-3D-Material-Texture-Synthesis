# Брокер сообщений: RabbitMQ или Kafka

Исследование 02.11.2026. Вопрос: оставить RabbitMQ (как в [03](03_API-сервис_оркестратор.md), [10](10_Инфраструктура.md), [12](12_Kubernetes_и_асинхронность.md)) или перейти на Apache Kafka. Источники проверены 02.11.2026 (Tavily, первоисточники — документация Celery, RabbitMQ, Apache Kafka, KEDA).

**Итог: оставить RabbitMQ.** Kafka не подходит как брокер задач Celery, у неё нет приоритетов, а долгие GPU-задачи плохо ложатся на модель «журнал + разделы». Единственный довод за Kafka — управляемый сервис в Selectel — не перевешивает.

## 1. Что брокер делает в нашей системе
| Задача | Как сейчас (RabbitMQ) |
|---|---|
| Конвейер `noise → generate → upscale → pbr` | Celery-цепочка, очереди `noise`, `gpu`, `cpu` |
| Премиум раньше бесплатных | приоритетная очередь `gpu` (`x-max-priority`); в Selectel — отдельные группы нод `gpu-premium` и `gpu-free` ([18](18_Развёртывание_в_Selectel.md)) |
| Долгие задачи на видеокарте (десятки секунд — минуты), одна задача на GPU | подтверждение после выполнения (`acks_late`), prefetch 1; при прерывании ноды задача возвращается в очередь |
| Повторы и упавшие задачи | до 3 попыток, затем dead-letter очередь |
| Статусы в БД ровно один раз | общая очередь `status-updates`, конкурирующие потребители |
| Прогресс в WebSocket без «липких» сессий | у каждой реплики API своя временная очередь, привязанная к `job.<id>.#` (topic exchange) |
| Масштабирование воркеров | KEDA по длине очереди, до нуля |
| Письма, статус запроса (ЛР4: `РеестрЗапросов.ОбновитьСтатус()`) | сообщения в очереди |

Нагрузка — единицы и десятки задач в минуту: узкое место — видеокарты, а не брокер. Пропускная способность Kafka (её главное преимущество) системе не нужна.

## 2. Чем они отличаются
- **RabbitMQ** — брокер очередей: сообщение доставляется одному потребителю, подтверждается и удаляется; маршрутизация обменниками (direct, topic, fanout), приоритеты, срок жизни, dead-letter, отложенные повторы.
- **Kafka** — распределённый журнал: записи хранятся по сроку хранения, потребитель читает по смещению; параллелизм ограничен числом разделов (partitions), порядок — внутри раздела; можно перечитать историю. С версии 4.2 (февраль 2026) готовы к эксплуатации **share groups** (KIP-932, «Queues for Kafka») — очередь поверх журнала: несколько потребителей читают один раздел, подтверждение и счётчик доставок у каждой записи, тип подтверждения RENEW для долгой обработки.
- Даже Confluent (компания-разработчик Kafka) в своём сравнении относит долгие фоновые задачи и очереди задач к сильным сторонам RabbitMQ, а Kafka — к потокам данных и их хранению.

## 3. Сравнение по нашим требованиям
| Требование | RabbitMQ | Kafka |
|---|---|---|
| Брокер для Celery | брокер по умолчанию; кворумные очереди поддерживаются с Celery 5.5 | транспорт kombu на confluent-kafka; документация Celery 5.7: «using Kafka as a broker means that only one worker can be used» (kombu #1785) — **наш конвейер с несколькими воркерами на Kafka не запустить** |
| Приоритет премиума | RabbitMQ 4.3 (23.04.2026): **32 строгих уровня приоритета** в кворумных очередях; у классических — `x-max-priority` | приоритетов нет; только отдельные топики и своя логика выбора |
| Долгие GPU-задачи | подтверждение после выполнения; тайм-аут подтверждения по умолчанию 30 минут, настраивается политикой (в 4.3 действует для кворумных очередей) | обычная группа потребителей: если обработка дольше `max.poll.interval.ms` (по умолчанию 5 минут), потребитель исключается из группы и начинается перебалансировка; записи одного раздела ждут друг друга. Share groups снимают это ограничение, но Celery их не использует |
| Повторы и упавшие задачи | dead-letter, лимит доставок у кворумной очереди, отложенные повторы (4.3) | повторы — через свои retry-топики |
| Прогресс в WebSocket по `job.<id>.#` | topic exchange, временная очередь на реплику | каждая реплика читает весь топик и фильтрует сама |
| Масштабирование KEDA | по длине очереди, до нуля | по отставанию (lag); по умолчанию реплик не больше числа разделов (`allowIdleConsumers: false`) |
| Хранение и повторное чтение событий | не основное назначение (есть RabbitMQ Streams) | сильная сторона |
| Управляемый сервис в Selectel | нет — только в кластере (RabbitMQ Cluster Operator), см. [18](18_Развёртывание_в_Selectel.md); управляемый RabbitMQ есть, например, у Timeweb Cloud | есть Managed Kafka |

## 4. Решение и что поменять
1. **Брокер — RabbitMQ**, Kafka не вводим. Если позже понадобятся хранение и повторное чтение событий для аналитики (публикации, открытия ссылок, этапы конвейера), это отдельный журнал событий (RabbitMQ Streams или Kafka рядом), а не замена брокера задач.
2. **Версия и тип очередей:** RabbitMQ 4.3, рабочие очереди — **кворумные** (реплицируются между узлами кластера и переживают потерю ноды; Celery для надёжности рекомендует переходить на них с зеркалируемых классических очередей). В Celery 5.5+: `task_default_queue_type = "quorum"`, `broker_transport_options = {"confirm_publish": True}`.
3. **Ограничения Celery на кворумных очередях** (документация Celery):
   - глобальный QoS отключён — `--autoscale` Celery и уменьшение prefetch не работают. У нас воркеры масштабирует KEDA подами, а prefetch и так 1;
   - задачи с ETA/countdown (в том числе `retry(countdown=…)`) идут через native delayed delivery — Celery включает её сам.
4. **Приоритеты:** строгие приоритеты могут бесконечно задерживать бесплатные задачи при постоянном потоке премиум-задач (предупреждение в документации RabbitMQ). Раз у тарифов разные группы GPU-нод, проще развести их по разным очередям (`gpu-premium`, `gpu-free`) и не смешивать приоритеты в одной очереди. Внутри очереди приоритет нужен только для коротких очередей `noise` и `cpu`.
5. **Тайм-аут подтверждения:** самая долгая GPU-задача (4 варианта по 4096² с апскейлом) должна укладываться в 30 минут. Иначе тайм-аут увеличивается политикой `consumer-timeout` для очереди `gpu-*`.
6. Вопрос 8 из [11](11_Решения_и_вопросы.md) (где разместить RabbitMQ) остаётся: в Selectel — в кластере через Cluster Operator.
