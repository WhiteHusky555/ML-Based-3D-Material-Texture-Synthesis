# Vaadin для интерфейса (исследование 13.11.2026)

Вопрос: можно ли написать фронтенд на Vaadin и для какой части системы это подходит.
Связано с решением писать административную часть на Kotlin + Ktor ([22](22_Kotlin_и_Ktor_для_администрирования.md)).

**Решение 13.11.2026:** вариант B. Панели персонала — Vaadin-приложение `staff-ui` (Kotlin, Spring Boot 4), оно же staff-BFF; за ним `admin-service` на Ktor. Генератор остаётся React + web-bff. Команды `staff-ui` отправляет через RabbitMQ, итог показывает через `@Push` ([24](24_Асинхронное_взаимодействие_outbox_inbox.md)).

## 1. Коротко
- **Генератор пользователей и страница снимка для гостя — Vaadin не рекомендую.** Состояние интерфейса каждого посетителя хранится в памяти сервера. Нужны sticky-сессии, а переживать падение пода без потери сеанса позволяет только платный Kubernetes Kit. Ползунки, 3D на Three.js и прогресс генерации всё равно останутся JS-кодом. Это противоречит принятой схеме: BFF без состояния, масштабирование по нагрузке.
- **Панели персонала — подходят хорошо.** Там таблицы, формы, фильтры, отчёты, единицы одновременных пользователей и короткие сеансы. Vaadin-приложение держит интерфейс на сервере, браузер получает только cookie сеанса. Тем самым оно само выполняет роль staff-bff и заменяет React-панели и отдельный staff-bff.
- **Vaadin не работает поверх Ktor:** официальной интеграции нет, ему нужен сервлет-контейнер. Поэтому при Vaadin на Ktor остаётся только сервис администрирования.

## 2. Что такое Vaadin сейчас (проверено)
- **Версия.** Vaadin 25: первый выпуск 17.12.2025, актуальная версия 25.3.5; Vaadin 25.4 запланирован на IV квартал 2026. Требования: Java 21+, Spring Boot 4 / Spring 7 (Boot 3 больше не поддерживается), Jakarta EE 11, Quarkus 3.27+, Node.js 24+, Gradle 8.14+. Внутри — React 19.
- **Flow и Hilla.** Flow — интерфейс пишется на Java или Kotlin и выполняется на сервере. Hilla — React с типизированными вызовами сервера; в Vaadin 25 подключается отдельно. По ответу на форуме Vaadin (неофициально), новых функций Hilla после 25 не будет.
- **Лицензия.** Ядро и большинство компонентов — Apache 2.0, бесплатно и для коммерческого использования. По подписке: Charts, Spreadsheet, TestBench, Designer, Kubernetes Kit. В части подписок есть модель оплаты по ежедневно активным пользователям (DAU).
- **Kotlin.** Библиотека Karibu-DSL — интерфейс в стиле Kotlin DSL. Проект Vaadin-on-Kotlin: Vaadin Boot — встроенный Jetty, запускаемый из `main()`, без Spring и отдельного сервлет-контейнера; Flyway для миграций; Karibu-Testing — тесты интерфейса в той же JVM, без браузера.
- **Обновления с сервера.** Server push включается аннотацией `@Push`. Транспорт по умолчанию — WebSocket + XHR (фреймворк Atmosphere); запасной вариант — long polling; SSE — экспериментально.
- **Сторонние JS-библиотеки.** Аннотации `@NpmPackage`, `@JsModule`, `@Tag` подключают веб-компоненты и модули JS; вызовы — через Element API (`callJsFunction`, `executeJs`). React-компоненты встраиваются через `ReactAdapterComponent`.
- **Память и масштабирование.** По данным блога Vaadin: 50 КБ – 1 МБ на сеанс пользователя (у большинства приложений меньше 500 КБ), 100–200 МБ кучи у простаивающего приложения, 1000–2000 пользователей на 1 ГБ кучи. Sticky-сессии обязательны — так ответили на форуме Vaadin. Kubernetes Kit (платный) сочетает sticky-сессии с асинхронной репликацией сеансов в Hazelcast или Redis — для отказоустойчивости и обновлений без разрыва сеансов.
- **Развёртывание.** Приложение — это сервлет: Spring Boot, Jakarta EE, Quarkus или Vaadin Boot (Jetty). Интеграции с Ktor в источниках нет.

Не проверял: встроенную защиту Vaadin от CSRF; бесплатные альтернативы Vaadin Charts (ECharts, Chart.js через `@JsModule`) — возможность подключения следует из механизма интеграции JS, но готовых обёрток я не смотрел.

## 3. Применимость к частям системы
| Часть | Что ей нужно | Как с Vaadin | Вывод |
|---|---|---|---|
| Генератор (пользователи) | ползунки шума с мгновенным превью, 3D-просмотр на Three.js, прогресс по WebSocket, публичный сервис с большим числом пользователей, BFF без состояния и масштабирование по нагрузке | каждое действие — запрос к серверу; состояние каждого пользователя в памяти; sticky-сессии; отказоустойчивость — только с платным Kubernetes Kit; Three.js подключается через `@JsModule`, то есть основа экрана всё равно на JS | не рекомендую; остаётся React + web-bff |
| Страница снимка для гостя (UC10) | анонимные посетители по ссылкам, их может быть много | состояние на сервере на каждого анонимного посетителя | не рекомендую |
| Панели персонала (администратор, аналитик, владелец) | таблицы с поиском и фильтрами, формы с проверкой, отчёты и графики, единицы одновременных пользователей, отдельный хост `staff.<домен>` | бесплатные Grid, формы и проверка ввода; графики — платные Vaadin Charts или бесплатная JS-библиотека через `@JsModule`; браузер получает только cookie, токены остаются на сервере — как в решении от 02.11.2026; sticky-сессий для двух реплик достаточно, при потере пода сотрудник входит заново | **подходит** |

## 4. Как Vaadin сочетается с Kotlin и Ktor
- **Две части на JVM.** Панели персонала — Vaadin-приложение на Kotlin (Karibu-DSL) на Vaadin Boot (Jetty, без Spring) или на Spring Boot 4. За ним — сервис администрирования на Ktor (REST API).
- **Сеанс сотрудника** — сессия сервлета в памяти пода, не Redis. Токены, полученные у сервиса пользователей, лежат в `VaadinSession` на сервере.
- **Мгновенный отзыв** надо сделать явно: `verify` перед каждым переходом между экранами и перед каждой командой, меняющей данные. Иначе блокировка подействует только при следующем переходе. Это требование правил проекта: отзыв действует сразу.
- **Маршрутизация.** nginx направляет хост `staff.` на Vaadin-приложение с привязкой по cookie: директива `sticky cookie`, в открытом nginx — с версии 1.29.6, раньше только в NGINX Plus. Redis для персонала не нужен.

## 6. Что поменяется при варианте B
- **Веб-клиент:** уходят React-панели персонала (окна администратора, аналитика, владельца). В ЛР4 эти граничные классы с теми же именами становятся экранами Vaadin.
- **Компоненты:** staff-bff на Python уходит; появляются `staff-ui` (Vaadin, Kotlin) и `admin-service` (Ktor). Хост `staff.` в nginx ведёт на `staff-ui` с привязкой по cookie.
- **Kubernetes:** Deployment `staff-ui` (2 реплики, привязка сеанса) и `admin-service`. Redis остаётся только у web-bff.
- **Документы:** те же, что в [22](22_Kotlin_и_Ktor_для_администрирования.md), плюс [02](02_Веб-клиент.md) — без панелей персонала; ЛР5–ЛР6 — «где работает» у панелей персонала; ЛР7–ЛР8 — компоненты `staff-ui` и `admin-service` (Gradle → JAR → образ).

## 7. Как связаны staff-ui (Vaadin) и веб-клиент (React, JS)
- **Напрямую — никак.** Это два независимых фронтенда на разных хостах:
  - `app.<домен>` — React + Three.js: статика от nginx, данные через web-bff;
  - `staff.<домен>` — Vaadin: интерфейс выполняется на сервере.
  
  Общего кода у них нет, друг друга они не вызывают.
- **Общая у них серверная часть:** те же сервисы-владельцы данных (сервис пользователей, API-сервис, `admin-service`) и тот же брокер. Изменения из панели доходят до генератора событиями. Пример: администратор меняет пресет → `preset.changed` → API-сервис обновляет копию пресетов → при следующем открытии генератора пользователь видит новый пресет.
- **Учётные записи общие, сеансы разные.** Сотрудник входит теми же e-mail и паролем (сервис пользователей). Но cookie с префиксом `__Host-` привязаны к своему хосту, поэтому сеанс генератора не открывает панели, и наоборот (решение 02.11.2026). У Vaadin это сеанс сервлета; cookie переименовывается в `__Host-texgen-staff-sid` настройкой сервера (`server.servlet.session.cookie.name` в Spring Boot).
- **JS внутри Vaadin:**
  - у Vaadin свой JS-клиент в браузере (веб-компоненты, внутри — React 19). Он собирается автоматически при сборке приложения, писать на JS ничего не нужно;
  - свой JS подключается точечно: веб-компонент — через `@NpmPackage`, `@JsModule`, `@Tag`; вызовы из Kotlin — через `executeJs` или `callJsFunction`; React-компонент — через `ReactAdapterComponent`;
  - у нас это нужно для графиков аналитика: бесплатная JS-библиотека вместо платных Vaadin Charts. Если понадобится 3D-просмотр материала в панели администратора — Three.js как веб-компонент тем же способом.
- **Единый внешний вид.** Общие цвета и шрифты задаются CSS-переменными: в React — обычным CSS, в Vaadin — в теме Lumo, которая тоже построена на CSS-переменных. Сами значения — из DESIGN.md при реализации.

## 8. Два фронтенда — правильно ли (пересмотр 14.11.2026)
Вопрос пользователя: насколько правильно, что фронтендов два (генератор на React и панели персонала на Vaadin). Решение: **оставить вариант B**.

**Разделение на два фронтенда — правильное:**
- **Разные пользователи и задачи.** Генератор — публичный: много пользователей, 3D, ползунки, растущая нагрузка. Панели — внутренние: единицы сотрудников, таблицы, формы, отчёты.
- **Изоляция.** У панелей отдельный хост, своя cookie, короткий сеанс, строгие лимиты, при необходимости список разрешённых IP. Уязвимость генератора не даёт доступа к панелям, а код панелей не попадает в сборку для всех пользователей.
- **Независимые выпуски.** Генератор и панели обновляются отдельно.
- **Так и задуман паттерн BFF:** отдельный BFF на каждый вид интерфейса ([16](16_Паттерн_BFF.md)).

**Цена разных технологий (React и Vaadin):**
- три языка в системе: TypeScript, Kotlin, Python;
- две сборки интерфейса;
- общий вид держится через CSS-переменные, компоненты у двух частей разные;
- выбор нужно обосновать в тексте ВКР.

**Рассмотренные варианты:**

| Вариант | Фронтенды | Языков | Комментарий |
|---|---|---|---|
| **B (оставлен)** | React + Vaadin | 3 | на компонент меньше (staff-ui сам себе BFF); два стека интерфейса |
| A | React-генератор + React-панели отдельной сборкой + staff-bff | 2, если staff-bff на Python | одна технология интерфейса, изоляция та же, компонентов больше |
| Одно React-приложение с разделом персонала по роли | 1 | 2 | меньше всего работы, но слабее изоляция: код панелей уходит всем, сеанс общий |

**Обоснование для ВКР:** для внутренних таблиц и форм Vaadin даёт готовые компоненты; интерфейс и токены персонала остаются на сервере; отдельный staff-bff не нужен. Генератору нужны 3D и масштабирование без состояния — поэтому React + web-bff.
