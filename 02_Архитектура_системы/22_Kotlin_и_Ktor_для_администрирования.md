# Kotlin и Ktor для административной части (исследование 13.11.2026)

Вопрос: подходят ли Kotlin и Ktor для административной части системы и чего это стоит.
Выбор пользователя от 13.11.2026: на Kotlin + Ktor пишутся **staff-bff** и **новый сервис администрирования**. Окончательная форма зависит от решения по Vaadin ([23](23_Vaadin_для_интерфейса.md)).

**Решение 13.11.2026:** вариант B. staff-bff на Ktor не нужен — роль BFF выполняет Vaadin-приложение `staff-ui`. На Ktor остаётся только `admin-service`. Показатели и финансы он берёт через внутренние API владельцев данных. События — через outbox и inbox ([24](24_Асинхронное_взаимодействие_outbox_inbox.md)). Раздел «staff-bff на Ktor» ниже сохранён как история исследования.

## 1. Коротко
- Ktor подходит для обеих частей. Всё нужное есть плагинами Ktor или стандартными библиотеками JVM: сеансы с хранением на сервере, CSRF, клиент HTTP на корутинах, метрики, трассировка, сборка Docker-образа.
- Главная цена — второй стек рядом с Python: JVM, Gradle, отдельный CI и образы с JRE. Вдобавок логику `bff-core` придётся написать второй раз, а контракты Python ↔ Kotlin — держать в OpenAPI.
- Две вещи придётся сделать самим. Хранилище сеансов в Redis: в Ktor встроены только память и каталог. И клиент к Python-сервисам: шаблоны OpenAPI Generator для Ktor устарели.

## 2. Что проверено (Ktor 3.6.1, Exposed 1.0)
| Что нужно | Чем закрывается | Проверено по |
|---|---|---|
| Сеанс на сервере, браузеру — только идентификатор в cookie | Плагин Sessions: данные сеанса на сервере, клиенту — подписанный идентификатор. Встроены хранение в памяти и в каталоге, своё хранилище — через интерфейс `SessionStorage`. С 3.5.0 (15.05.2026) cookie можно отправлять только при изменении сеанса | документация Sessions, «What's new in 3.5.0» |
| Redis для сеансов | Клиент Lettuce с API на корутинах Kotlin. API экспериментальный и требует явного согласия (`@ExperimentalLettuceCoroutinesApi`) | руководство Lettuce |
| Защита от CSRF | Плагин CSRF с Ktor 3.0 (2024): проверка Origin, совпадения с хостом, обязательного заголовка | блог JetBrains о Ktor 3.0, справочник API |
| Работа с БД без сырого SQL | Exposed 1.0 (январь 2026): типобезопасный DSL и лёгкий DAO, драйверы JDBC и R2DBC | блог JetBrains, репозиторий Exposed |
| Миграции схемы инструментом | Exposed сравнивает описание таблиц с БД и генерирует SQL-скрипты миграций (`exposed-migration-jdbc`, плагин Gradle), но сам их не применяет — применяет Flyway или Liquibase | документация Exposed «Migrations» |
| События через RabbitMQ | Официальный Java-клиент `amqp-client` 5.36.0, JDK 8 и новее | rabbitmq.com |
| Метрики и трассировка | Плагин MicrometerMetrics (в том числе Prometheus), плагин OpenTelemetry `KtorServerTelemetry` (артефакт `opentelemetry-ktor-3.0`, версия alpha) | документация Ktor |
| Образ для Kubernetes | Fat JAR или исполняемое JVM-приложение. Плагин Ktor для Gradle собирает Docker-образ (Jib) с заданной версией JRE. Возможен native image GraalVM, но нужна конфигурация отражения | документация Ktor: Deployment, Docker, GraalVM |
| Контракты с сервисами на Python | FastAPI отдаёт `openapi.json`, из него можно сгенерировать Kotlin-клиент (OpenAPI Generator, `library=jvm-ktor` или `multiplatform`). Но в документации генератора эти шаблоны указаны с **Ktor 1.6.7** — клиент устаревший. Надёжнее генерировать только модели данных, а вызовы писать на клиенте Ktor 3.x | документация OpenAPI Generator |

Не проверял: память, которую реально занимает Ktor-сервис в поде; тестовый движок Ktor; размер native image.

## 3. Как это ложится на архитектуру
### staff-bff на Ktor
- Делает то же, что сейчас ([17](17_Предложение_внедрения_BFF.md)):
  - сеанс сотрудника по cookie `__Host-texgen-staff-sid` (30 минут бездействия, не больше 12 часов);
  - на каждый запрос — `/internal/auth/verify` сервиса пользователей без кэша (мгновенный отзыв по `token_version`);
  - CSRF, лимиты, сборка экранов панелей.
- web-bff остаётся на Python с `bff-core`. В staff-bff то же поведение пишется на Kotlin: сеанс в Redis (общий экземпляр, свой префикс ключей), вызов `verify`, клиент к сервисам с таймаутами, единый формат ошибок (StatusPages).
- Чтобы поведение web-bff и staff-bff не разошлось: общий контракт в OpenAPI (формат ошибок, заголовки `X-User-Id` и роли) и контрактные тесты.

### Сервис администрирования на Ktor
- **Становится владельцем данных** только для персонала: пресеты и версии модели (переходят из API-сервиса), журнал аудита (из сервиса пользователей). Схема `admin` в PostgreSQL; доступ через Exposed, миграции — Flyway.
- **Только читает:** мониторинг, показатели для аналитика, финансовый отчёт.
- **Остаётся в сервисе пользователей** как у владельца данных: блокировка пользователей, роли, тарифы. staff-bff вызывает для этого сервис пользователей.
- **События через RabbitMQ:**
  - «опубликована версия модели» → GPU-воркеры подгружают веса;
  - «изменён пресет» → API-сервис сбрасывает кэш;
  - записи аудита от сервиса пользователей и API-сервиса приходят в сервис администрирования событиями. Запись идемпотентная: ключ события, outbox у отправителя, повтор не создаёт дубля.
- **Показатели и финансы** — два варианта: внутренние API владельцев (просто, но много запросов) или реплика БД только для чтения с отдельной ролью (удобно для агрегатов). Решено 13.11.2026: внутренние API владельцев.

## 4. Цена и риски
| Риск | Что делать |
|---|---|
| Второй стек: JVM, Gradle, свой CI, образы с JRE | Один шаблон Gradle-проекта для обоих Kotlin-сервисов; образ собирает плагин Ktor |
| Логика сеансов в двух реализациях (Python и Kotlin) расходится | Контракт в OpenAPI и контрактные тесты на вход, выход, истёкший сеанс и отзыв роли |
| Устаревшие шаблоны генератора клиентов для Ktor | Генерировать только модели, вызовы писать на клиенте Ktor 3.x |
| Корутинный API Lettuce экспериментальный | Зафиксировать версию; хранилище сеансов — небольшой модуль, его легко заменить |
| Плагин OpenTelemetry для Ktor — alpha | Метрики — через Micrometer (стабильно), трассировку включить после проверки |
| Память JVM в подах больше, чем у Python-сервисов | Запросы памяти задать после замера, а не по оценке |
| В ВКР больше объяснять | Обоснование в тексте: язык выбран под задачи персонала (типизация, JVM-библиотеки для отчётов) |

## 5. Вывод
Kotlin + Ktor применимы для staff-bff и сервиса администрирования без технических препятствий. Цена — второй стек и повтор логики сеансов. Если панели персонала будут на Vaadin ([23](23_Vaadin_для_интерфейса.md)), отдельный staff-bff не нужен: Vaadin-приложение само выполняет роль BFF. Тогда на Ktor остаётся только сервис администрирования.
