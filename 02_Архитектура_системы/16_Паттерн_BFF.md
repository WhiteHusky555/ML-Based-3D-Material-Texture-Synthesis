# Паттерн BFF (Backend for Frontend)

Исследование 27.10.2026. Пересматривает решение 14.10.2026 «агрегация запросов (BFF) не нужна» из [01](01_nginx_API-шлюз.md). Конкретное предложение по внедрению — [17](17_Предложение_внедрения_BFF.md).

## 1. Что это такое
- **BFF** — отдельный серверный компонент для каждого типа интерфейса (веб, мобильное приложение, сторонние клиенты) вместо одного общего API для всех. BFF принадлежит своему интерфейсу: собирает данные из нескольких сервисов, приводит их к форме, удобной конкретному экрану, и скрывает внутреннее устройство системы.
- Паттерн возник в SoundCloud около 2011 г., название и описание дал Сэм Ньюмен (S. Newman, «Pattern: Backends For Frontends», книга «Building Microservices»). Microsoft включила его в каталог облачных паттернов Azure Architecture Center, AWS описывает его в связке с паттерном «издатель — подписчик».
- С 2026 г. BFF — ещё и **официальная рекомендация по безопасности**: RFC 10017 (BCP 212) «OAuth 2.0 for Browser-Based Applications» ставит архитектуру с BFF первой (самой защищённой) из вариантов для браузерных приложений. Токены хранятся только на сервере, браузер получает лишь cookie сеанса с флагами `HttpOnly`, `Secure`, `SameSite=Strict`, поэтому вредоносный JavaScript (XSS) не может украсть токены.

## 2. Чем BFF отличается от API-шлюза
| | API-шлюз (nginx в нашей системе) | BFF |
|---|---|---|
| Сколько | один на всю систему | по одному на тип интерфейса |
| Задача | сквозные функции: единая точка входа, TLS, маршрутизация, лимиты, статика | данные под конкретный интерфейс: агрегация, преобразование, сеанс пользователя |
| Знает об экранах | нет | да, API BFF проектируется от экранов |
| Где стоит | на краю системы | за шлюзом, перед сервисами |
| Бизнес-логика | нет | нет — правила тарифов, квоты, права остаются в сервисах |

Паттерны не исключают друг друга: типичная схема — шлюз на краю, за ним BFF, за BFF — сервисы (так её описывает, например, Флант в обзоре API-шлюзов: шлюз маршрутизирует запросы фронтенда к соответствующему BFF).

## 3. Зачем BFF в нашей системе
1. **Безопасность токенов.** Сейчас access-токен JWT (15 мин) лежит в памяти браузера, а refresh-токен — в httpOnly cookie ([02](02_Веб-клиент.md), [09](09_Сервис_пользователей_и_тарифы.md)). При XSS скрипт может прочитать access-токен и обращаться к API от имени пользователя, в том числе с другого устройства. С BFF в браузере нет ни одного токена: только cookie сеанса, которую скрипт прочитать не может. Это ровно вариант, который рекомендует RFC 10017.
2. **Два разных интерфейса.** Пользовательское приложение (генератор, история, 3D-просмотр, тарифы) и панели персонала (администратор, аналитик, владелец) различаются данными, частотой изменений и требованиями к безопасности. Панели работают с персональными данными, ролями и финансами — их разумно отделить от пользовательского API: отдельный адрес, свои лимиты, свой журнал, меньше поверхность атаки.
3. **Агрегация данных для экранов.** Почти каждый экран собирает данные из двух-трёх сервисов:

| Экран | Что нужно | Откуда сейчас |
|---|---|---|
| Генератор | пресеты, права тарифа, остаток квоты | API-сервис + сервис пользователей — 2–3 запроса из браузера |
| История | материалы, срок хранения по тарифу | API-сервис + сервис пользователей |
| 3D-просмотр | метаданные материала, временные ссылки S3 на 5 карт | API-сервис, ссылки — отдельными запросами |
| Аналитика | отчёты по пользователям и подпискам, статистика генераций | сервис пользователей + API-сервис |
| Пользователи (админ) | учётная запись, тариф, число генераций | сервис пользователей + API-сервис |

   BFF делает это одним запросом из браузера, параллельные внутренние вызовы идут по быстрой сети кластера.
4. **Будущие клиенты.** Плагины для Blender и Unity (у аналогов есть работа прямо из редактора: Scenario импортирует материалы в Unity, генератор материалов Unity встроен в редактор — см. `03_Аналоги`) — это третий тип клиента с другой аутентификацией (ключ API или OAuth device flow) и другими данными. С BFF он добавляется отдельным компонентом, сервисы не меняются.

## 4. Когда BFF не нужен и чем он опасен
- **Ньюмен:** если интерфейс только веб и серверной агрегации мало, BFF не окупается. У нас есть второй интерфейс (панели персонала), заметная агрегация и довод безопасности, поэтому условие для BFF выполняется.
- **Ещё один сетевой переход:** +1–3 мс на запрос внутри кластера. Для нас некритично: долгие операции и так асинхронные (`202` + WebSocket).
- **Дублирование сквозной логики** между несколькими BFF (проверка сеанса, лимиты, журналы). Решается общей библиотекой и тем, что лимиты по IP остаются в nginx.
- **«Толстый» BFF:** соблазн перенести в него бизнес-правила (квоты, тарифы). Правило: BFF только собирает и преобразует данные, решения принимают сервисы-владельцы данных.
- **Состояние:** сеансы надо где-то хранить (Redis или PostgreSQL), а сервис без состояния проще масштабировать. Решается внешним хранилищем сеансов: реплики BFF остаются без локального состояния.

## 5. Варианты для системы
| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| A. Без BFF (как сейчас) | браузер ходит в сервисы через nginx | меньше компонентов | токен доступа в браузере; агрегация на клиенте; панели персонала на общем API |
| B. Один BFF для веба | один компонент для пользователей и персонала | токены на сервере, агрегация | смешаны пользовательский API и API персонала, общий релизный цикл и общая поверхность атаки |
| **C. Два BFF** | **web-bff** (пользователи) и **staff-bff** (персонал) | всё из B; панели персонала изолированы: отдельный хост, строже лимиты, свой журнал | два компонента вместо одного (оба небольшие, общая библиотека) |
| D. C + BFF для плагинов | третий BFF для Blender/Unity | готовность к новым клиентам | плагинов в ВКР нет — компонент без потребителя |

## 6. Вывод
- Рекомендую **вариант C**: web-bff и staff-bff за nginx, сеансы в Redis, токены не покидают сервер. Вариант D — в перспективы развития: BFF для плагинов появляется вместе с самими плагинами.
- nginx остаётся API-шлюзом (TLS, статика, маршрутизация, лимиты по IP); проверку сеанса и агрегацию берут на себя BFF.
- В тексте ВКР: «API-шлюз (nginx) + BFF для каждого типа интерфейса», обоснование — разд. 3, ссылки — Newman, Microsoft, RFC 10017.
