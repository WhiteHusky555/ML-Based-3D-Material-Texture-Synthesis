# API-сервис (оркестратор) — FastAPI

Владелец материалов и задач генерации. Пользователей и тарифы не хранит — получает `X-User-Id`, `X-User-Plan` и `X-User-Role` от шлюза, а лимиты тарифа читает у сервиса пользователей (с кэшированием).

## Эндпоинты
| Метод и путь | Назначение |
|---|---|
| `POST /api/materials` | создать задачу генерации |
| `GET /api/materials/{id}` | статус, ссылки на карты |
| `GET /api/materials` | история пользователя (постранично) |
| `DELETE /api/materials/{id}` | удалить материал / отменить задачу |
| `GET /api/materials/{id}/download?engine=unity` | ZIP под движок (presigned-ссылка MinIO) |
| `GET /api/presets` | пресеты материалов |
| `WS /ws/jobs/{id}` | прогресс задачи |
| `POST/PUT /api/admin/presets[/{id}]` | создать или изменить пресет (роль admin), запись в журнал аудита |
| `POST /api/admin/models` | загрузить версию весов LoRA, проверка совместимости и пробная генерация (роль admin) |
| `GET /api/analytics/generations?from=&to=` | агрегаты по генерациям: пресеты, время этапов, доля кэша, отмены и ошибки (роли analyst, owner) |

## Обработка `POST /api/materials`
1. **Проверка прав тарифа** (entitlements): разрешение, модель, число вариантов, суточная квота. Нарушение → `403` с понятным текстом («4096² доступно в Премиум») или `429` («лимит 10 генераций на сегодня исчерпан»).
2. **Кэш по хэшу** параметров. Хэш: шум + промпт + seed + разрешение + версии SD / ControlNet / LoRA / апскейлера + версия кода конвейера.
   - Бесплатные пользователи используют **общий кэш** — экономия GPU.
   - **Премиум-результаты в общий кэш не попадают** (в ключ входит `user_id`): у премиума коммерческая лицензия без атрибуции, его материалы не должны доставаться другим.
3. Запись материала с `expires_at` = сейчас + срок хранения тарифа.
4. Celery-цепочка `noise → generate → upscale → pbr`, маршрутизация по очередям `noise`, `gpu`, `cpu`, **приоритет по тарифу** (премиум выше). Шум тоже считается в очереди — API-сервис ничего не ждёт.
5. **Ответ `202 Accepted`** с id задачи. Дальше клиент следит за прогрессом по WebSocket.

Сервис полностью асинхронный: async FastAPI, asyncpg, aio-pika. Состояния в памяти нет, поэтому реплик может быть сколько угодно (см. [12](12_Kubernetes_и_асинхронность.md)).

## Состояния задачи
`created → noise → generating → upscaling → pbr → done / failed / cancelled`.
Время входа в каждый этап пишется в таблицу `stages` — из неё берутся метрики ВКР.

## Поэтапный кэш
Отдельные хэши: шума, генерации, PBR-настроек. Поменяли только силу нормалей — пересчитывается один PBR-этап за секунды, GPU не нужен.

## События
- Воркеры публикуют в topic-exchange `job.events` (routing key `job.<id>.<stage>`).
- **Запись в БД:** общая durable-очередь `status-updates`, которую слушают все реплики как конкурирующие потребители — каждое событие записывается ровно один раз.
- **Доставка в WebSocket:** у каждой реплики своя временная очередь; когда клиент открывает сокет для задачи, реплика привязывает очередь к `job.<id>.#`. Событие приходит туда, где открыт сокет, — «липкие» сессии не нужны.
- **В таблицы материалов пишет только API-сервис**, воркеры в базу не ходят: у данных один владелец.

## Срок хранения
- **Kubernetes CronJob** (раз в час) находит материалы с `expires_at < now()`, удаляет объекты из S3 и строки из БД, публикует событие. Celery beat не используется: при нескольких репликах он запускал бы задачу несколько раз.
- При оформлении премиума у существующих материалов пользователя `expires_at` продлевается до срока премиума; при отмене — возвращается к сроку бесплатного тарифа, считая от даты отмены (уточнить правило в [11_Решения_и_вопросы.md](11_Решения_и_вопросы.md)).

## Таблицы (схема `core`)
- `materials` (id, user_id, params jsonb, params_hash, plan_at_creation, status, created_at, expires_at)
- `stages` (material_id, stage, started_at, finished_at, gpu_mem_peak, worker)
- `artifacts` (material_id, kind, s3_key, width, height, format, bytes)
- `presets` (id, name, noise jsonb, prompt_template, base_roughness, premium_only)
- Миграции — Alembic.
