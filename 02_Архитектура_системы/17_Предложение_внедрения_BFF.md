# Предложение: внедрение BFF в архитектуру системы

27.10.2026. **Статус: предложение, решение не принято.** Основание — исследование [16](16_Паттерн_BFF.md) (вариант C: два BFF). Пока решение не принято, остальные документы описывают текущую схему без BFF.

## 1. Целевая схема
```
Браузер: React + Three.js — токенов нет, только cookie сеанса (__Host-, HttpOnly, Secure, SameSite=Strict)
   │  HTTPS
   ▼
Балансировщик → nginx ×N (API-шлюз): TLS, статика, лимиты по IP, маршрутизация по хосту и пути
   ├── app.<домен>   /bff/*, /bff/ws/*  → web-bff ×N   ─┐
   ├── staff.<домен> /staff/*           → staff-bff ×N ─┤── сеансы и кэш превью: Redis
   │                                                    ▼
   │                         внутренняя сеть кластера (NetworkPolicy: в сервисы — только из BFF)
   │     Пользователи и тарифы · API-сервис (+ WebSocket) · Процедурный сервис · Ассистент промптов
   │                                                    │ задачи / события
   │                                              RabbitMQ → воркеры (без изменений)
   └── presigned URL → S3 (скачивание напрямую из хранилища; ссылки выдаёт BFF)
```
Воркеры, очереди, конвейер генерации и владение данными не меняются: BFF стоят между шлюзом и сервисами и своей базы данных не имеют.

## 2. Компоненты
| Компонент | Для кого | Стек | Реплики | Состояние |
|---|---|---|---|---|
| **web-bff** | пользователи (бесплатный и премиум-тариф) | Python, async FastAPI, httpx — как остальные сервисы | 2+, HPA по CPU | нет: сеансы в Redis |
| **staff-bff** | администратор, аналитик, владелец | тот же стек и общая библиотека `bff-core` | 2 | нет: сеансы в Redis |
| **Redis** | сеансы обоих BFF, кэш превью шума | управляемый (Selectel / ElastiCache) или Redis в кластере; локально — контейнер в Compose | 1 + реплика | данные сеансов с TTL |

**Что делает BFF:** ведёт сеанс пользователя и хранит токены у себя; на каждый запрос проверяет сеанс; собирает данные экрана из нескольких сервисов параллельно (`asyncio.gather`, таймаут на каждый вызов); приводит ответ к форме экрана; проксирует WebSocket прогресса.
**Чего BFF не делает:** не проверяет квоты и права тарифа, не хранит материалы и пользователей, не кэширует права и роли. Решения по-прежнему принимают сервисы-владельцы данных.

## 3. Аутентификация и сеансы
### Вход
1. Браузер: `POST /bff/auth/login` с e-mail и паролем.
2. web-bff передаёт их сервису пользователей (`/internal/auth/login`), получает access-токен JWT (15 мин) и refresh-токен (30 дней).
3. web-bff создаёт сеанс в Redis: ключ — случайный идентификатор (256 бит), значение — пользователь, токены, срок; TTL сеанса — 30 дней от входа, бездействие — 7 дней.
4. Ответ: `Set-Cookie: __Host-texgen-sid=…; Path=/; Secure; HttpOnly; SameSite=Strict`. Токены в браузер не попадают.

### Каждый запрос
1. BFF находит сеанс по cookie. Нет сеанса → `401`, клиент показывает вход.
2. Истёк access-токен → BFF сам обновляет его через сервис пользователей (с ротацией refresh-токена) и сохраняет в сеансе.
3. BFF вызывает `/internal/auth/verify` **без кэширования**. Сервис пользователей читает статус, роль и `token_version`, поэтому блокировка или отзыв роли действуют со следующего запроса (требование мгновенного отзыва). Ответ — те же `X-User-Id`, `X-User-Plan`, `X-User-Role`, что сейчас ставит nginx.
4. BFF вызывает сервисы с этими заголовками. **Сервисы не меняются**: они по-прежнему доверяют заголовкам, а снаружи до них не достать.

### Защита от CSRF и выход
- Cookie `SameSite=Strict`, обязательный заголовок `X-Requested-With: texgen` на изменяющих запросах (форма с чужого сайта его не поставит) и проверка `Origin` — меры, которые перечисляет RFC 10017 для BFF.
- `POST /bff/auth/logout`: сеанс удаляется из Redis, refresh-токен отзывается в сервисе пользователей, cookie стирается.
- Блокировка администратором: сервис пользователей увеличивает `token_version` → следующий `verify` отклоняет запрос → BFF удаляет сеанс и отвечает `401`.

### Особенности staff-bff
- Отдельный хост `staff.<домен>` и своя cookie `__Host-texgen-staff-sid`: сеанс пользовательского приложения не даёт доступа к панелям.
- Короче сеанс: бездействие 30 минут, не больше 12 часов от входа.
- Сеанс создаётся только для учётных записей с ролью `admin`, `analyst` или `owner`; конкретные права по-прежнему проверяют сервисы.
- Жёстче `limit_req` в nginx; при необходимости — список разрешённых IP. Двухфакторный вход — в перспективы развития.

## 4. API web-bff
| Метод и путь | Экран | Что возвращает | Внутренние вызовы |
|---|---|---|---|
| `POST /bff/auth/login`, `/logout`, `/register`, `/password/*` | вход | сеанс (cookie), ошибки входа | сервис пользователей |
| `GET /bff/me` | все | профиль, тариф, остаток квоты, роли | сервис пользователей |
| `GET /bff/generator` | генератор | пресеты, права тарифа, остаток квоты, доступность премиум-опций — **один запрос вместо трёх** | API-сервис + сервис пользователей |
| `GET /bff/noise/preview` | генератор | плитка превью; кэш в Redis по параметрам шума (раньше — `proxy_cache` nginx, но проверка сеанса теперь в BFF) | процедурный сервис |
| `POST /bff/assistant/hints` | генератор | подсказки (премиум) | ассистент промптов |
| `POST /bff/materials` | генератор | `202` + id задачи; ключ идемпотентности передаётся дальше | API-сервис |
| `WS /bff/ws/jobs/{id}` | генератор | прогресс задачи | API-сервис (WebSocket) |
| `GET /bff/history?page=` | история | материалы с миниатюрами и **оставшимся сроком хранения в днях** | API-сервис + сервис пользователей |
| `GET /bff/materials/{id}/view` | 3D-просмотр | метаданные и пять временных ссылок S3 одним ответом | API-сервис |
| `POST /bff/materials/{id}/export` | результат | ссылка на архив | API-сервис |
| `GET /bff/billing`, `POST /bff/billing/subscribe`, `/cancel` | тариф | тарифы, текущая подписка; оформление и отмена | сервис пользователей |

## 6. Изменения в существующих компонентах
| Компонент | Что меняется |
|---|---|
| nginx ([01](01_nginx_API-шлюз.md)) | маршруты `/bff/` и `/bff/ws/` → web-bff, хост `staff.` → staff-bff; прямые маршруты `/api/*` и `auth_request` убираются (проверку сеанса делает BFF); TLS, статика и лимиты по IP остаются |
| Веб-клиент ([02](02_Веб-клиент.md)) | токены и логика их обновления удаляются; запросы идут на `/bff` того же источника, cookie прикрепляется браузером; на `401` — экран входа; панели персонала — отдельная сборка на `staff.` |
| Сервис пользователей ([09](09_Сервис_пользователей_и_тарифы.md)) | вход и обновление токена становятся внутренними (их вызывает BFF); `verify`, `token_version`, хэши refresh-токенов — без изменений |
| API-сервис ([03](03_API-сервис_оркестратор.md)) | WebSocket принимает подключения от web-bff с заголовком `X-User-Id` вместо проверки в nginx; остальное без изменений |
| Инфраструктура ([10](10_Инфраструктура.md)) | добавляется Redis |
| Kubernetes ([12](12_Kubernetes_и_асинхронность.md)) | два Deployment, HPA для web-bff, PodDisruptionBudget, NetworkPolicy «в сервисы — только из BFF»; фраза «сессии — в JWT» меняется на «сеансы — в Redis», липкие сессии по-прежнему не нужны |

## 7. Влияние на лабораторные работы
- **ЛР1** (прецеденты) не меняется: BFF — внутренний компонент, для акторов поведение системы то же.
- **ЛР2, ЛР3:** в UC1 действие «Выдача токенов доступа» и состояние «Выдача токенов» станут «Созданием сеанса» (токены остаются на сервере, браузер получает cookie сеанса); поправлю после принятия решения.
- **ЛР5** (последовательности): хороший сценарий для диаграммы — «Открытие генератора»: браузер → web-bff → параллельно API-сервис и сервис пользователей → один ответ.
- **ЛР7, ЛР8** (компоненты, размещение): web-bff, staff-bff и Redis появятся как компоненты и узлы.

## 9. Риски
| Риск | Что делаю |
|---|---|
| Redis недоступен — никто не может работать | управляемый Redis с репликой; при сбое — `503` с понятным сообщением; перезапуск BFF сеансы не теряет |
| Лишний сетевой переход | замер задержки на шаге 4; агрегация сокращает число запросов из браузера, суммарно ответ быстрее |
| BFF обрастает бизнес-логикой | правило «BFF только собирает и преобразует данные», проверка на ревью |
| Много WebSocket-соединений через BFF | асинхронный BFF; при росте — отдельный прокси для WebSocket |
| CSRF из-за cookie | `SameSite=Strict` + обязательный заголовок + проверка `Origin` |
