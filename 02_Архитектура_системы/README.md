# Архитектура системы генерации бесшовных PBR-материалов

Актуально на 16.10.2026. Учтены решения: роли персонала (администратор, аналитик, владелец); nginx как API-шлюз; ассистент — всплывающие подсказки (премиум); пользователи и тарифы; **все сервисы асинхронные и масштабируются в ширину; запуск в Kubernetes; облако, предварительно AWS**; LLM для подсказок — локальная модель или OpenRouter.

## Схема

```
Браузер: React + Three.js
   │  HTTPS: REST, WebSocket, JWT
   ▼
AWS NLB → nginx ×N (API-шлюз): статика, маршруты, проверка JWT (auth_request), лимиты, WebSocket, кэш превью
   ├── /api/auth, /api/me, /api/billing, /api/owner, /api/admin/users → Пользователи и тарифы ×N → PostgreSQL (схема users)
   ├── /api/noise                       → Процедурный сервис, API превью ×N
   ├── /api/assistant                   → Ассистент промптов ×N (премиум) → LLM: Ollama/vLLM в кластере или OpenRouter
   ├── /api, /ws                        → API-сервис ×N → PostgreSQL (схема core)
   │                                          │ задачи ↓ (приоритет по тарифу)   ↑ события
   │                                       RabbitMQ
   │                                          ├── noise → процедурный воркер ×N (KEDA)
   │                                          ├── gpu   → GPU-воркер ×N: генерация → апскейл (KEDA + Karpenter)
   │                                          └── cpu   → PBR-воркер ×N (KEDA)
   └── presigned URL                    → Amazon S3 (MinIO при локальной разработке)

Kubernetes (Amazon EKS), Helm-чарт texgen; CronJob очистки по сроку хранения
```

## Поток создания материала

1. Ползунки → `/api/noise/preview` → процедурный сервис (пул процессов) отдаёт плитку; nginx кэширует повторы.
2. (Премиум) описание → ассистент после паузы присылает 1–3 подсказки.
3. «Сгенерировать» → `POST /api/materials`: шлюз проверил JWT → API-сервис проверяет тариф, квоту и кэш → ставит Celery-цепочку `noise → generate → upscale → pbr` с приоритетом тарифа → **сразу отвечает `202` с id задачи**.
4. Воркеры по очереди выполняют этапы, файлы пишут в S3, события публикуют в RabbitMQ.
5. API-сервис: одна реплика записывает событие в БД, а реплика, у которой открыт WebSocket клиента, пересылает прогресс.
6. 3D-просмотр, скачивание ZIP по presigned-ссылке S3.
7. CronJob удаляет материалы с истёкшим сроком хранения.

## Ключевые принципы
- **Асинхронность:** неблокирующий ввод-вывод везде; всё долгое — через очереди; клиент узнаёт о готовности по WebSocket.
- **Масштабирование в ширину:** сервисы без состояния, по нескольку реплик; воркеры добавляются по длине очереди.
- **Бесшовность на каждом этапе:** периодический шум → циклический padding в UNet, ControlNet и VAE → wrap-паддинг при апскейле → wrap-фильтры в PBR.
- **Один владелец данных:** материалы пишет только API-сервис, пользователей — только сервис пользователей.
- **Роли:** пользователь, администратор, аналитик, владелец; права проверяются на сервере при каждом запросе, действия персонала пишутся в журнал аудита (см. [09](09_Сервис_пользователей_и_тарифы.md)).
- **GPU — главная статья расходов:** на GPU только диффузия и апскейл, по задаче на видеокарту; spot и масштабирование до нуля для бесплатного тарифа.
- **Заменяемые провайдеры:** модель генерации и LLM подключаются через интерфейсы.
- **Docker + Kubernetes:** образы собираются Docker; для ежедневной разработки — Docker Compose, для облака и проверки масштабирования — Kubernetes (Helm).
