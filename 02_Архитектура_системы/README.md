## Граница НИР и ВКР

В НИР входят подготовка данных и обучение одной LoRA для SD 1.5 в Kaggle, разработка сервиса процедурных шумов и сборка конвейера от карты шума до комплекта PBR-карт. Конвейер включает генерацию через ControlNet, апскейл и расчёт карт. В НИР проверяются управляемость генерации, качество текстур и бесшовность. В ВКР этот конвейер включается в облачную обработку задач с API, очередями, хранилищем и веб-интерфейсом. В пояснительной записке ВКР описываются разработка конвейера, обучение модели и эксперименты НИР. [План НИР](../05_Нейросетевые_модели/09_База_датасет_и_дистилляция.md).

## Схема

```text
Пользователи: браузер, React + Three.js       Персонал: браузер, панели Vaadin
                        HTTPS / WebSocket
                               │
                  AWS NLB → nginx (TLS, маршруты, лимиты по IP)
   ├── app.<домен>   /                → статика React
   ├── app.<домен>   /bff/, /bff/ws/  → web-bff (Python / FastAPI)
   │     ├── Redis: пользовательские сеансы и кэш превью
   │     ├── HTTP: пользователи и тарифы, API-сервис, превью шума, ассистент
   │     └── WebSocket: прогресс из API-сервиса в браузер
   ├── staff.<домен> /                → staff-ui (Vaadin / Kotlin / Spring Boot)
   │     ├── Сеанс в памяти пода, привязка по cookie в nginx
   │     ├── HTTP: пользователи и тарифы, admin-service, чтение показателей
   │     └── Vaadin Push: итоги команд и обновления панели
   └── POST /api/billing/webhook      → сервис пользователей (подпись провайдера)

web-bff, staff-ui ── команды ──► RabbitMQ ──► сервисы-владельцы (Inbox)
   API-сервис           ──► PostgreSQL: core  (материалы, запросы)
   Пользователи и тарифы ──► PostgreSQL: users (учётные записи, тарифы, подписки)
   admin-service (Ktor) ──► PostgreSQL: admin (пресеты, версии модели, аудит)
   Сервисы с БД ── результаты и доменные события через Outbox ──► RabbitMQ

API-сервис ── задачи через Outbox ──► RabbitMQ: noise / gpu / cpu
   noise → процедурный воркер → gpu → [GPU-воркер: сервис генерации → сервис апскейла (Real-ESRGAN)] → cpu → PBR-воркер
   Воркеры ──► S3: файлы материалов
   Воркеры ──► RabbitMQ ──► API-сервис: события этапов
   Браузер ── по временной подписанной ссылке ──► S3: просмотр и скачивание

Kubernetes (предварительно Amazon EKS), Helm-чарт texgen
```

Оба BFF хранят токены на сервере и вызывают `/internal/auth/verify` без кэширования для защищённых запросов. Внутренние сервисы изолированы через NetworkPolicy. Вебхук оплаты проходит по выделенному маршруту, S3 выдаёт файлы по подписанным ссылкам. События журнала аудита потребляет `admin-service`. Ассистент обращается к Ollama или vLLM в кластере либо к OpenRouter. Воркеры масштабируются по очередям через KEDA, GPU-узлы в EKS — через Karpenter. CronJob удаляет материалы с истёкшим сроком хранения.

## Поток создания материала

1. Ползунки → `/bff/noise/preview` → web-bff (кэш в Redis) → процедурный сервис (пул процессов) отдаёт плитку.
2. (Премиум) описание → ассистент после паузы присылает 1–3 подсказки.
3. «Сгенерировать» → `POST /bff/materials`. web-bff проверяет сеанс (verify без кэша), публикует команду `core.request.create` с новым id задачи и после подтверждения брокера **отвечает `202`**. Дальше API-сервис:
   - отсекает повтор через inbox;
   - проверяет тариф, квоту и кэш;
   - в одной транзакции пишет материал и строку outbox;
   - ретранслятор ставит Celery-цепочку `noise → generate → upscale → pbr` с приоритетом тарифа;
   - отказ (тариф, квота) приходит клиенту событием по WebSocket.
4. Воркеры по очереди выполняют этапы, файлы пишут в S3, события публикуют в RabbitMQ.
5. API-сервис: одна реплика записывает событие в БД, а реплика, у которой открыт WebSocket клиента, пересылает прогресс.
6. 3D-просмотр, скачивание ZIP по presigned-ссылке S3.
7. CronJob удаляет материалы с истёкшим сроком хранения.

## Ключевые принципы
- **Асинхронность:** неблокирующий ввод-вывод везде; всё долгое — через очереди; клиент узнаёт о готовности по WebSocket.
- **Команды и события — через брокер** (с 13.11.2026): outbox у отправителя, inbox у получателя, доставка «хотя бы один раз», потребители идемпотентны. Синхронно (HTTP) — чтение для экранов, аутентификация, регистрация и операции подписки ([24](24_Асинхронное_взаимодействие_outbox_inbox.md)).
- **Масштабирование в ширину:** компоненты разворачиваются в нескольких репликах. Для `staff-ui` требуется привязка сеанса к поду, а воркеры добавляются по длине очереди.
- **Бесшовность на каждом этапе:** периодический шум → циклический padding в UNet, ControlNet и VAE → wrap-паддинг при апскейле → wrap-фильтры в PBR.
- **Один владелец данных:** материалы пишет только API-сервис, пользователей — только сервис пользователей, пресеты, версии модели и журнал аудита — только `admin-service`; другие сервисы держат копии, обновляемые событиями.
- **Роли:** пользователь, администратор, аналитик, владелец; права проверяются на сервере при каждом запросе, действия персонала пишутся в журнал аудита (см. [09](09_Сервис_пользователей_и_тарифы.md)).
- **GPU — главная статья расходов:** на GPU только диффузия и апскейл, по задаче на видеокарту; spot и масштабирование до нуля для бесплатного тарифа.
- **Заменяемые провайдеры:** модель генерации и LLM подключаются через интерфейсы.
- **Docker + Kubernetes:** образы собираются Docker; для ежедневной разработки — Docker Compose, для облака и проверки масштабирования — Kubernetes (Helm).

## Очереди сервисного стенда НИР

Три очереди стенда НИР соответствуют трём вычислительным этапам: noise, generation и pbr. Схема Compose, HTTP-контракт и запуск приведены в [README НИР](../06_НИР/README.md). В облачной схеме очереди GPU и PBR исторически обозначены gpu и cpu.

## Документация HTTP API

Каждый сервис, предоставляющий HTTP API, поставляет спецификацию OpenAPI и Swagger UI. При добавлении маршрута в том же изменении описываются входные параметры, успешный ответ, формат данных и ошибки. В локальном стенде спецификация доступна по `/openapi.json`, интерфейс — по `/docs`. Доступ к схемам внутренних сервисов в облаке ограничен внутренней сетью.

| HTTP-сервис НИР | Swagger UI | Операции |
|---|---|---|
| Задания | [8010/docs](http://127.0.0.1:8010/docs) | Постановка задания, состояние, скачивание PNG |
| Шум | [8011/docs](http://127.0.0.1:8011/docs) | Расчёт карты высот |
| Генерация | [8012/docs](http://127.0.0.1:8012/docs) | Готовность модели, генерация albedo, параметр upscale |
| PBR | [8013/docs](http://127.0.0.1:8013/docs) | Расчёт height, normal, roughness и AO |

[Апскейл](06_Сервис_апскейла.md) выделен в логический сервис и использует общий GPU-воркер с генерацией. В стенде через `POST /generate` можно включить Lanczos ×2. Для целевого этапа Real-ESRGAN предусмотрена задача GPU-воркера. Контракты задач и событий RabbitMQ описаны в [схеме асинхронного взаимодействия](24_Асинхронное_взаимодействие_outbox_inbox.md).
