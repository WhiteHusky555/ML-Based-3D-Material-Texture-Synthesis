# nginx — API-шлюз

## Почему nginx, а не отдельный API Gateway
- В этой системе отдельный шлюз (Kong, Traefik, KrakenD) поверх nginx дублировал бы функции и добавил бы контейнер и задержку. Kong сам построен на nginx (OpenResty).
- В тексте ВКР: паттерн **«API-шлюз» (API Gateway)**, реализация — **nginx**.
- За шлюзом — **BFF** (решение 02.11.2026, [17](17_Предложение_внедрения_BFF.md)): web-bff для пользователей и staff-bff для персонала. Проверку сеанса и сборку данных экранов делают они; nginx — TLS, статика, лимиты по IP и маршрутизация.

## Функции шлюза
| Функция | Как реализуется |
|---|---|
| Единая точка входа | наружу публикуется только порт nginx (80/443), остальные контейнеры во внутренней сети Docker Compose |
| Раздача статики | собранный React-клиент, `try_files $uri /index.html` для маршрутов SPA, долгий кэш для файлов с хэшем в имени |
| Маршрутизация | по префиксу пути (таблица ниже) |
| **Аутентификация** | не в шлюзе: сеанс (cookie) проверяет BFF и на каждый запрос вызывает `/internal/auth/verify` сервиса пользователей без кэша; заголовки `X-User-Id`, `X-User-Plan`, `X-User-Role` ставит сервисам BFF |
| Ограничение частоты | `limit_req` по IP (защита от перебора и спама); тарифные квоты считает API-сервис |
| WebSocket | `proxy_http_version 1.1`, заголовки `Upgrade`/`Connection`, `proxy_read_timeout 1h` |
| Кэш превью шума | в Redis у web-bff по параметрам шума (`proxy_cache` nginx не используется: сеанс проверяется в BFF) |
| Трассировка | заголовок `X-Request-ID` на каждый запрос, сервисы пишут его в логи |
| Сжатие | gzip для JS/JSON (картинки уже сжаты) |
| TLS | по необходимости; локально можно без него |

## Маршруты
| Путь | Куда | Особенности |
|---|---|---|
| `/` | статика React | — |
| хост `app.<домен>`: `/bff/`, `/bff/ws/` | web-bff | жёсткий `limit_req` на `/bff/auth/` от перебора паролей; WebSocket прогресса; гостевые `/bff/shared/*` — без сеанса |
| хост `staff.<домен>`: `/staff/` | staff-bff | строже `limit_req`; при необходимости — список разрешённых IP |
| `POST /api/billing/webhook` | сервис пользователей | уведомления платёжной системы: без сеанса, подпись проверяет сервис |
| хост `s3.localhost` | MinIO | **без переписывания пути**: подпись presigned-URL S3 включает хост и путь; префикс `/files/` сломал бы подпись |

Прямых маршрутов `/api/*` к сервисам больше нет (кроме вебхука платёжной системы): сервисы закрыты NetworkPolicy и принимают запросы только от BFF.

## nginx в Kubernetes
- Свой nginx — **Deployment с 2+ репликами** и Service типа LoadBalancer (в AWS — Network Load Balancer через AWS Load Balancer Controller). Конфигурация та же, что в Docker Compose; адреса BFF и сервисов — внутренние DNS-имена Kubernetes (`api.texgen.svc`).
- **ingress-nginx не использовать:** проект официально выведен из поддержки в марте 2026 г. (обновлений и патчей безопасности больше нет).
- Альтернатива, «родная» для Kubernetes: **Gateway API** (NGINX Gateway Fabric, Envoy Gateway, Traefik). Проверка сеанса при этом остаётся в BFF и от выбора шлюза не зависит.
- Хост `s3.localhost` в облаке не нужен: presigned-ссылки ведут прямо в Amazon S3 (или через CloudFront).

## Почему проверка сеанса в BFF, а не в шлюзе
- Токены не попадают в браузер: их хранит BFF в сеансе (Redis), браузер получает только cookie `HttpOnly` — вариант, который RFC 10017 (BCP 212) считает самым защищённым для браузерных приложений.
- Каждый сервис по-прежнему получает уже проверенные `X-User-Id`, `X-User-Plan` и `X-User-Role` и не дублирует логику; ставит их BFF, а извне до сервисов не достать (NetworkPolicy).
- Ответ `/internal/auth/verify` **не кэшируется**: статус, роль и версия токенов читаются на каждый запрос, поэтому блокировка или отзыв роли действуют сразу (решение 16.10.2026). Нагрузка — один запрос по первичному ключу; при росте — реплики сервиса пользователей.
