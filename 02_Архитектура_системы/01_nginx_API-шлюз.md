# nginx — API-шлюз

## Почему nginx, а не отдельный API Gateway
- В этой системе отдельный шлюз (Kong, Traefik, KrakenD) поверх nginx дублировал бы функции и добавил бы контейнер и задержку. Kong сам построен на nginx (OpenResty).
- В тексте ВКР: паттерн **«API-шлюз» (API Gateway)**, реализация — **nginx**.
- Агрегация запросов (BFF): решение 14.10.2026 «не нужна» пересматривается — исследование [16](16_Паттерн_BFF.md), предложение [17](17_Предложение_внедрения_BFF.md) (nginx остаётся шлюзом, за ним — web-bff и staff-bff).

## Функции шлюза
| Функция | Как реализуется |
|---|---|
| Единая точка входа | наружу публикуется только порт nginx (80/443), остальные контейнеры во внутренней сети Docker Compose |
| Раздача статики | собранный React-клиент, `try_files $uri /index.html` для маршрутов SPA, долгий кэш для файлов с хэшем в имени |
| Маршрутизация | по префиксу пути (таблица ниже) |
| **Аутентификация** | `auth_request` на `/internal/auth/verify` сервиса пользователей: проверка JWT, в ответ заголовки `X-User-Id`, `X-User-Plan`, `X-User-Role` пробрасываются в сервисы |
| Ограничение частоты | `limit_req` по IP (защита от перебора и спама); тарифные квоты считает API-сервис |
| WebSocket | `proxy_http_version 1.1`, заголовки `Upgrade`/`Connection`, `proxy_read_timeout 1h` |
| Кэш превью шума | `proxy_cache` по URL: превью детерминировано параметрами |
| Трассировка | заголовок `X-Request-ID` на каждый запрос, сервисы пишут его в логи |
| Сжатие | gzip для JS/JSON (картинки уже сжаты) |
| TLS | по необходимости; локально можно без него |

## Маршруты
| Путь | Куда | Особенности |
|---|---|---|
| `/` | статика React | — |
| `/api/auth/` | сервис пользователей | без проверки JWT (вход, регистрация, обновление токена); жёсткий `limit_req` от перебора паролей |
| `/api/me`, `/api/billing/` | сервис пользователей | с проверкой JWT |
| `/api/admin/users`, `/api/owner/`, `/api/analytics/` | сервис пользователей | с проверкой JWT; роль (`admin`, `owner`, `analyst`) проверяет сервис по `X-User-Role` |
| `/api/admin/` (пресеты, модели), `/api/analytics/generations` | API-сервис | с проверкой JWT; роль проверяет сервис |
| `/api/noise/` | процедурный сервис | с проверкой JWT, `proxy_cache` |
| `/api/assistant/` | ассистент промптов | с проверкой JWT; доступ только для премиума проверяет сам ассистент по `X-User-Plan`; таймаут 60 с |
| `POST /api/materials` | API-сервис | с проверкой JWT; лимит по IP |
| `/api/`, `/ws/` | API-сервис | с проверкой JWT |
| хост `s3.localhost` | MinIO | **без переписывания пути**: подпись presigned-URL S3 включает хост и путь; префикс `/files/` сломал бы подпись |

## nginx в Kubernetes
- Свой nginx — **Deployment с 2+ репликами** и Service типа LoadBalancer (в AWS — Network Load Balancer через AWS Load Balancer Controller). Конфигурация та же, что в Docker Compose, включая `auth_request`; адреса сервисов — внутренние DNS-имена Kubernetes (`api.texgen.svc`).
- **ingress-nginx не использовать:** проект официально выведен из поддержки в марте 2026 г. (обновлений и патчей безопасности больше нет).
- Альтернатива, «родная» для Kubernetes: **Gateway API** (NGINX Gateway Fabric, Envoy Gateway, Traefik). Тогда проверка JWT делается средствами выбранного контроллера (внешняя авторизация / JWT-политики), а не `auth_request`.
- Хост `s3.localhost` в облаке не нужен: presigned-ссылки ведут прямо в Amazon S3 (или через CloudFront).

## Почему проверка JWT в шлюзе
- Каждый сервис получает уже проверенные `X-User-Id`, `X-User-Plan` и `X-User-Role` и не дублирует логику.
- Сервисы закрыты во внутренней сети, поэтому подделать заголовки извне нельзя — nginx перезаписывает их сам.
- Ответ `auth_request` **не кэшируется**: статус, роль и версия токенов читаются на каждый запрос, поэтому блокировка или отзыв роли действуют сразу (решение 16.10.2026). Нагрузка — один запрос по первичному ключу; при росте — реплики сервиса пользователей.
