# Оценка ЛР4 по DDD и правилам чистого кода (ub-mode) и внесённые исправления

Дата: 30.10.2026. Объект оценки — модель классов ЛР4 в редакции 27.10.2026 (56 классов, 77 отношений, 16 диаграмм).
Результат — редакция 30.10.2026 (71 класс, 94 отношения, 19 диаграмм), отчёт и рисунки пересобраны.

Ограничение: требования методички [5] (гл. 4) остаются главными — пакеты «Сущности», «Граничные классы», «Управляющие классы», стереотипы entity / boundary / control, три вида диаграмм, документирование каждого элемента. Приёмы DDD и чистого кода применены внутри этих рамок: роли DDD (корень агрегата, объект-значение, событие, контекст) записаны в документации классов, новых стереотипов нет.

## 1. Что изучено

**DDD — стратегические приёмы.** Единый язык (Ubiquitous Language): модель и разговор с экспертами используют одни и те же строгие термины [Fowler, UbiquitousLanguage]. Ограниченный контекст (Bounded Context): большая модель делится на контексты, у каждого своя согласованная модель, связи между ними описываются явно [Fowler, BoundedContext]. Защитный слой к внешним системам — интерфейс, который переводит чужую модель в свою.

**DDD — тактические приёмы.** Сущность — объект с идентичностью и жизненным циклом. Объект-значение — составное значение без идентичности, сравнивается по значению; примеры у Фаулера — «деньги = сумма + валюта», «период = начало + конец» [Fowler, ValueObject]. Агрегат — кластер объектов, который загружается и сохраняется целиком; внешние ссылки идут только на корень, транзакция не пересекает границу агрегата [Fowler, DDD_Aggregate]. Правила Вернона [Vernon, ч. I–II]: моделировать истинные инварианты внутри границы согласованности; проектировать малые агрегаты; ссылаться на другие агрегаты по идентификатору; вне границы использовать согласованность в конечном счёте (события). Анемичная модель — антипаттерн: объекты-«мешки» с данными, а вся логика в сервисах [Fowler, AnemicDomainModel].

**ub-mode** (unclebob/ub-mode, коммит 57a8bdd от 25.10.2026; установлен в `~/.claude/skills/ub-mode/SKILL.md`). Разделы, применимые к модели классов:
- Laziness Protocol — «одно решение живёт в одном месте»; Subtract Before You Add — сначала убрать сложность;
- Foundational Thinking — «сначала правильная форма данных, потом логика»; один писатель разделяемого состояния;
- Model the Domain — «структура, в которой недопустимые состояния невозможны»; «вести глоссарий терминов предметной области»;
- Boundary Discipline — проверять данные на входе, внутри доверять, бизнес-логику держать в чистых функциях;
- Type System Discipline — «недопустимое значение невозможно записать», внешние данные разбирать один раз на входе;
- Make Operations Idempotent; Keep a Log (журнал действий — разд. 6).

Разделы TDD, Crapper (CRAP < 10), Dryer, Mutator, Commit and Push относятся к коду и к ЛР4 неприменимы: в модели классов нет кода и тестов. Они понадобятся при реализации (ЛР7 и программная часть ВКР); коммиты и push делает автор, а не агент.

**Чистый код (Р. Мартин), применимое к сигнатурам:** разделение команд и запросов (операция либо меняет состояние, либо возвращает значение); имена операций — глаголы; без флаговых аргументов; исключения вместо кодов возврата; не возвращать null молча; один класс — одна причина для изменения (SRP); зависимость от абстракций (DIP). Сведения приведены по книге [Martin, 2008] без сверки страниц.

## 2. Оценка редакции 27.10.2026

Что уже соответствовало: разделение entity / boundary / control; интерфейсы ПлатёжнаяСистема и ПровайдерПодсказок — защитный слой и зависимость от абстракции; ключи идемпотентности (СоздатьМатериал, СуточныйСчётчик, Платёж); перечисления для жизненных циклов; проверка токена при каждом запросе без кэширования (мгновенный отзыв доступа); русские доменные имена, согласованные с ЛР1–ЛР3.

## 4. Что сознательно не менялось

- **Стереотипы.** Корни агрегатов, объекты-значения и события остаются «entity»: методичка [5] и пособие Каюмовой задают три стереотипа, роль DDD указана в документации класса.
- **Репозитории.** Отдельные интерфейсы хранилищ для каждого агрегата не введены: они удвоили бы число зависимостей на диаграммах, а в [5] доступ к БД — обязанность управляющих классов. Хранение через ORM (SQLAlchemy, без «сырого» SQL) будет показано на диаграмме компонентов ЛР7.
- **ШлюзПочты без интерфейса.** Одна реализация (SMTP), настройки из переменных окружения; в тестах подменяется заглушкой. Правило ub-mode: если и так ясно и локально — не трогать.
- **Активация версии модели.** `УправлениеВерсиямиМодели` при активации меняет две версии (старую и новую). Это редкое действие одного администратора; Вернон допускает изменение нескольких агрегатов в одной транзакции при такой «привязке пользователя» с оптимистической блокировкой.
- **Три параметра.** Операции с тремя аргументами (`СоздатьМатериал`, `ИзменитьТариф`, `Рассчитать`) оставлены: каждый аргумент — отдельное понятие, объект-параметр добавил бы класс без смысла.
- **Возврат токенов `dict` и `ВыбранноеДействие(): str` у окон** — транспортный формат и событие интерфейса, решений по ним в модели нет.
